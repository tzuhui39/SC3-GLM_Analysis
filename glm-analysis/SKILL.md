# 廣義線性模型（GLM）分析 skill

## 核心工作流程（完整分析模式的四個階段）

1. **探索性資料分析（EDA）**
2. **適合性評估**：這筆資料適不適合用 GLM？該用哪個分佈家族／連結函數？
3. **模型配適**：實際 `glm()` 配適，解釋係數
4. **模型診斷與評估**：檢查先前的假設與模型是否站得住腳

**所有階段開始之前**，先列出資料的全部變數；若使用者沒有說明哪個是反應變數（Y）、哪些是解釋變數（X），必須先詢問使用者並等到回覆，才能開始 EDA（細節見 Stage 1-0）。EDA 做完後，還要請使用者確認資料有沒有 typo 或奇怪的數值（尤其最大最小值），使用者確認沒問題才能進入 Stage 2（細節見 Stage 1-2）。

### 三種工作模式

先判斷使用者要的是哪一種，不要一律強迫從頭走完：

- **完整分析模式**：使用者給資料、要求做 GLM 分析或迴歸分析時，依序完成 Stage 1 到 4。四個階段都要在回覆中清楚分節、逐步說明「在做什麼、為什麼這樣做、結果代表什麼意思」，不省略步驟、不直接跳到結論。「不可跳步驟」只適用於這個模式。
- **指定步驟模式**：使用者只問某項診斷、某個係數的解釋、某個概念，或只要 EDA 時，直接處理該問題並完整解釋，不必重跑所有階段，也不必重新列變數、重新等待確認。
- **延續既有分析模式**：對話中前面的 EDA、模型配適已經完成，且資料與模型沒有改變時，直接接續，不重複要求使用者確認相同的內容。資料或模型一有變動（換變數、換模型、處理資料），就要重新做受影響部分的檢查。

### 統計判斷與自動化決策原則（所有階段共同遵守）

診斷指標是證據，不是自動決策規則。

1. 不得僅憑單一圖形、檢定 p 值或經驗門檻，自動宣告模型正確、錯誤或必須更換。
2. 每項診斷結果都必須結合資料結構、研究目的、模型假設及其他診斷證據解釋。
3. 發現問題時，先辨識可能原因，再提出適當的處理選項；不得將所有問題一律歸因於同一個模型假設。
4. 更換 family、link、函數形式或變數組合後，應重新配適模型，並重新執行相關診斷，不能假設單一修改已解決所有問題。
5. 若有多個合理模型，應說明各模型的優缺點、選模依據與限制；不得只因某模型的 p 值較小、AIC 較低或係數較容易解釋，就宣稱它是唯一正確的模型。
6. 最終結論必須與最終模型、研究目的及資料實際支持的證據一致；若證據不足，應明確說明不確定性，而不是強行產生確定結論。

### 何時暫停並與使用者討論

如果某個階段發現資料可能不適合直接套用 GLM（例如樣本數或事件數偏少、反應變數不屬於常見 GLM 家族、觀測值相依、模型無法識別），要在該階段停下來明確告知使用者問題所在，說明對估計、解釋或預測的影響，提出選項（換模型、資料轉換、蒐集更多資料、改用本 skill 不支援的方法等）並詢問要不要繼續。

共線性、樣本數偏少這類問題**通常不是停止分析的充分理由**：若共線性使特定係數無法穩定估計、模型無法識別，或使研究問題無法回答，才暫停該項推論並與使用者討論；若仍能合理配適，可以繼續分析，但必須說明它對估計、解釋或預測的影響。

## 環境設置（每次新對話 session 開始時，先做這件事）

不要假設環境已經有 R 或特定套件，也不要假設一定有某個工具或輸出路徑。每次進行分析前，先確認實際可用的 R 執行方式（例如能在 shell 執行 `Rscript`）與所需套件。若沒有 R 環境、或無法安裝，要明確告知使用者這個限制，**不要假裝已經執行了分析**，也不要編造輸出。以下以常見的 Linux 容器為例（容器可能在對話之間重置）：

```bash
which Rscript
```

如果沒有輸出（代表沒裝），先確認是否有權限安裝、安裝來源是否可用，再安裝 R 與本 skill 需要的核心套件（在測試過的容器中，apt 來源可正常安裝，不需要 CRAN 鏡像）：

```bash
apt-get install -y --no-install-recommends \
  r-base-core r-cran-mass r-cran-car r-cran-ggplot2 \
  r-cran-dplyr r-cran-performance r-cran-knitr r-cran-rmarkdown r-cran-broom
```

這會裝好：
- `MASS`：`glm.nb()` 負二項迴歸、`boxcox()`
- `car`：`vif()` 共線性、`Anova()`
- `ggplot2`：繪圖
- `dplyr`：資料整理
- `performance`：`check_overdispersion()`、`check_collinearity()`、`check_model()`、`r2()` 等一站式診斷
- `knitr`：`kable()` 出表格、產報告用
- `rmarkdown`：Quarto 執行 R 程式區塊時需要
- `broom`：`tidy()` / `glance()` 把模型結果整理成資料框

**只有要產出報告檔案時**才需要再裝 Quarto（pip 可以裝，已實測）：

```bash
pip install quarto-cli --break-system-packages
```

要輸出 PDF 時另外需要 LaTeX 與中文套件（已實測，缺少會出現 `lmodern.sty`、`xeCJK.sty not found`）：

```bash
apt-get install -y --no-install-recommends lmodern texlive-xetex \
  texlive-latex-recommended texlive-latex-extra texlive-fonts-recommended \
  texlive-lang-chinese texlive-lang-cjk fonts-noto-cjk
```

裝好之後用 `Rscript -e 'library(套件名)'` 快速確認沒有報錯即可繼續。實際分析一律用目前環境可用的 R 執行工具實際執行（例如在 shell 執行 `Rscript your_script.R`，或用 heredoc 寫檔後執行），把**真正的輸出**（模型摘要、檢定結果、圖檔）呈現給使用者，不要用記憶中的假輸出唬弄使用者。

**已知的環境陷阱（在測試過的容器中確認過）**：這個容器預設 locale 是 `POSIX`／`C`，不支援多位元組字元。如果 R 程式碼裡有中文（例如中文欄位名稱、`data.frame(中文欄位 = ...)`），會直接 parse error（`unexpected '<'` 之類的錯誤）。解法：**執行 `Rscript` 時一律在前面加上 `LC_ALL=C.UTF-8`**，例如：

```bash
LC_ALL=C.UTF-8 Rscript your_script.R
LC_ALL=C.UTF-8 quarto render report.qmd --to pdf
```

不要漏掉這個環境變數，否則只要程式碼或資料裡出現中文就會整段失敗。

另外，`performance::check_model(model)` 的畫圖功能需要額外的 `see` 套件，這個套件在此環境不一定能透過 apt 裝到。**預設請改用 base R 內建的 `plot(model)`（四合一診斷圖：Residuals vs Fitted、Normal Q-Q、Scale-Location、Residuals vs Leverage）當作總覽圖**，`check_overdispersion()`、`vif()` 等純文字輸出的診斷函式不受影響可正常使用。

## R 程式碼撰寫規範（硬性規定，務必遵守）

1. **絕對不要用 `---` 當作視覺分隔線**（不管是在 R 程式碼註解、對話文字、章節之間都不行）。唯一例外：Quarto（qmd）檔案最上方的 YAML frontmatter 語法上「必須」用 `---` 包住（例如 `--- \n title: ... \n ---`），這是 qmd 檔案格式的硬性語法，不算違反規則；但除了那個 YAML 區塊之外，檔案內文完全不要再出現 `---`。要分段就用中文標題（`##`、`###`）或空行分隔，不要畫線。
2. **絕對不要使用 `kableExtra::kable_styling()`**。表格一律用 `knitr::kable()` 本身輸出就好（在對話中可直接 `print()` 或用 `kable(x)`），不要再疊加 `kable_styling()` 或其他 kableExtra 的樣式函式。若使用者要求要更漂亮的表格排版，改用 `knitr::kable(..., format = "pipe")` 或直接呈現整理過的資料框，不要用 `kable_styling()`。
3. 程式碼中文註解要寫清楚每一步在做什麼。程式碼只出現在背景執行與報告檔案（qmd）中；在對話回覆裡不要貼 R 程式碼，使用者明確要求時才提供。
4. 圖表用 `ggplot2`，存成 `.png` 後用環境提供的圖片檢視或檔案傳送功能展示給使用者看，不要只描述圖長怎樣。

## Stage 1：探索性資料分析（EDA）

拿到資料後，**第一件事永遠是列出資料中的所有變數**，並確認哪個是反應變數（Y）、哪些是解釋變數（X），確認完才往下做。

### Stage 1-0：列出所有變數，確認 X / Y、研究目的與時間順序（必做，在任何分析之前）

1. 讀入資料後，先列出全部變數，用表格呈現（`knitr::kable()`，不要用 `kable_styling()`），至少包含：變數名稱、資料型態（numeric / integer / factor / character / logical）、不重複值個數、遺漏值個數、前幾個範例值。可用下面的寫法：

```r
var_tbl <- data.frame(
  變數名稱 = names(dat),
  資料型態 = sapply(dat, function(x) class(x)[1]),
  相異值個數 = sapply(dat, function(x) length(unique(x))),
  遺漏值個數 = sapply(dat, function(x) sum(is.na(x))),
  範例值 = sapply(dat, function(x) paste(head(unique(x), 3), collapse = ", ")),
  row.names = NULL
)
knitr::kable(var_tbl)
```

2. **判斷使用者有沒有說明 X 與 Y**：
   - 使用者已明確指出（例如「Y 是 count，X 是 age 和 sex」「以 outcome 為反應變數」）：照使用者說的做，並在列出變數後複述一次「反應變數：○○；解釋變數：△△、□□」讓使用者確認。
   - 使用者**沒有**說明（只丟資料、只說「幫我做 GLM／迴歸分析」）：**不要自己猜、不要直接開始分析**。列完變數表後，停下來詢問（若環境有選擇題式的提問工具就用它，否則用純文字提問）：
     1. 哪一個變數是**反應變數（Y，想被預測或解釋的結果）**？
     2. 哪些變數是**解釋變數（X，用來預測或解釋 Y 的變數）**？哪些變數不要放進模型（例如編號 ID、日期、重複資訊的欄位）？
     
     提問時可以根據變數名稱與型態給出「建議」（例如「`id` 看起來是編號，建議排除」「`count` 是非負整數，可能是反應變數」），但建議只是供選擇，仍必須等使用者回覆確認後才進行後續步驟。
   - 使用者只說了 Y 沒說 X：就只詢問 X（哪些要納入、哪些排除），反之亦然。
3. 如果有計數資料的暴露量（offset，例如觀察人年數、面積）或二元資料的分組試驗總數，也要在這一步順便問清楚它是哪一個變數。
4. **確認研究問題與時間順序（配適任何模型之前必做）**：先讀 `references/model-building-and-validation.md` 的 A 節，然後
   - 問使用者研究目的是**解釋關聯**、**推論因果**，還是**建立預測模型**（使用者已說明就複述確認即可）。目的不同，後面選變數、選模型、評估方式都不同。
   - 逐一檢查解釋變數。「記錄在結果之後」與「變數本身在結果之後才產生」並不相同，對可疑變數要分別釐清：**變數實際發生或存在的時間**、**被測量或記錄的時間**、**是否可能受到 Y 影響**，並對照研究目的。把這些列給使用者，詢問要排除還是保留，不要自行決定；因果推論不能只憑時間先後決定調整與否，預測則要看預測時點是否取得得到該變數；保留可疑變數時要在結論中交代可能的偏誤。
5. 使用者確認後，把確認結果寫成一段話（「研究目的：○○；反應變數：○○；解釋變數：△△、□□；排除：××；可能在結果之後才產生的變數：××」），後續所有階段都以這個設定為準。若之後發現設定有問題（例如 Y 其實不適合 GLM），回頭向使用者說明再討論，不要私自更改。

### Stage 1-1 以後：探索性資料分析

確認 X / Y 之後，至少做這些事，並逐項說明看到了什麼、代表什麼：

1. **資料結構**：`str(dat)` / `dplyr::glimpse(dat)`，確認每個欄位的型態（數值、因子、字元）是否符合預期。
2. **反應變數（Y）的分佈**：
   - 畫 histogram 或 bar chart（連續 vs 類別）
   - 印出 `summary(y)`；若是計數資料，順便算 `mean(y)` 和 `var(y)`，先初步感受一下有沒有 mean ≈ var（poisson 的假設）或 var >> mean（可能過度離散）
3. **遺漏值**：`colSums(is.na(dat))`，報告各變數的缺失比例，說明可能的處理方式（刪除、插補，視情況建議）。**不得在未說明的情況下把缺失值當成 0 或用平均數填補**；使用完整個案分析要說明可能的偏誤；需要插補時要考慮缺失機制，並與使用者確認（細節見 `references/model-building-and-validation.md` 的 G 節）。配適模型後，還要報告模型實際使用的樣本數與因缺失被排除的筆數。
4. **解釋變數（X）與 Y 的關係**：連續 X 用散佈圖 + smooth line，類別 X 用 boxplot／分組長條圖，讓使用者先看到「大概的關係方向」。
5. **解釋變數彼此之間**：連續變數之間看相關係數矩陣（`cor()`），初步警覺潛在的共線性問題（正式檢定留到 Stage 4 用 VIF）。

這階段的產出是「對這筆資料的整體理解」，還沒有要做任何推論或配模型，語氣上要像是在幫使用者「認識資料」。

### Stage 1-2：資料檢查關卡（完整分析模式下，EDA 做完後的預設做法）

EDA 結果呈現完之後，**預設先停下來讓使用者確認資料有沒有問題**，不要自己判斷「看起來還好」就繼續。要特別把容易出現打字錯誤（typo）或奇怪數值的地方整理給使用者看：

1. **數值變數的最小值與最大值**：用一張表列出每個數值變數的最小值、最大值、平均、中位數，最大最小值要明顯可見。
2. **類別變數的所有類別與各類別個數**：用來抓拼字不一致（例如 `Male`／`male`／`M`）、多餘空白、不該出現的類別。
3. **分析流程要主動標出可疑之處**，並指出是哪個變數、哪個值：
   - 計數資料出現負數或小數
   - 二元變數出現 0／1 以外的值
   - 超出常理的值（例如年齡 200、比例大於 1、金額為負）
   - 離群很遠的極端值（例如超出 1.5 倍 IQR 很多）
   - 欄位型態與內容不符（例如數值欄位被讀成文字）
4. 表格與可疑項目呈現完後，直接問使用者：**「最大最小值和各類別有沒有看起來不對的地方？可能是打錯字、單位錯誤或奇怪的數值？」** 可用 `AskUserQuestion` 提供「資料沒問題，繼續」「有問題，我來說明」兩個選項，工具不可用時用純文字詢問，然後等使用者回覆。

使用者回覆後：
- **說資料沒問題**：直接進入 Stage 2。
- **指出有問題**：問清楚要怎麼處理（改成正確值、設為遺漏值、排除該筆觀測值），照使用者指示處理，不要自行決定。處理完後重新呈現受影響變數的最小值／最大值／類別，再確認一次，確認沒問題才進入 Stage 2。
- 如果沒有發現任何可疑之處，也要照樣呈現最小值與最大值並請使用者確認，因為只有使用者知道什麼數值在他們的情境中合理。

**這個關卡的例外**（避免一律卡住）：
- 發現可能的資料錯誤、異常編碼，或會改變模型結論的疑點時，**必須**停下來詢問，不能略過。
- 使用者明確要求教學示範、純探索性分析，或明確授權「資料沒問題，直接分析」時，可以繼續，但要在後續的結果與報告中**標示這些資料品質限制尚未由使用者確認**。
- 延續既有分析模式且資料沒有改變時，不必重複確認。

要產出報告檔案時，這張最大最小值表與可疑項目的說明也要放進報告的 EDA 章節。

## Stage 2：適合性評估——這筆資料適合 GLM 嗎？該選哪個 family / link？

先**確認資料結構**，再決定能不能直接套用一般 GLM：
- **相關觀測**：有沒有重複測量、同一個人／家庭／學校的多筆資料、群聚或巢狀結構？有的話，一般 GLM 的獨立性假設可能不成立，可能需要 GLMM、GEE 或其他方法，**這超出本 skill 的支援範圍**，要誠實告知並說明，不要假裝一般 GLM 已經處理好。
- **暴露量（offset）**：計數資料若各觀測的觀察時間、人年數、面積不同，要先確認是否需要 offset。
- **完全分離的跡象**：二元資料若某個變數幾乎完全決定 Y，要先辨識（見 `references/model-building-and-validation.md` 的 F 節）。
- **樣本數與事件數**：樣本數是否足夠要綜合判斷（事件比例、稀有事件、參數個數、資料分布與估計方法）；「每個參數 10–20 筆」只是粗略的經驗法則，不是准入標準，偏少時要明講估計可能不穩定。
- **極端值與資料輸入錯誤**：是否有需要先處理的問題。

接著依「反應變數的型態」建立**候選模型**。詳細的判斷邏輯放在 `references/family-link-selection.md`，**進入這個階段時務必先讀取那份參考檔案**。依反應變數型態選 family/link 只是候選模型的起點，**不能僅憑 Y 的直方圖、偏態或整體平均數與變異數就宣稱分布假設成立**；要同時考慮研究問題、觀測值的獨立性、資料產生機制，以及解釋變數與 Y 的條件關係，並在配適後以診斷確認。若有多個合理候選，就保留並比較。

判斷完後，用一小段文字講清楚：「反應變數是 XX 型態 → 先以 YY 分佈、ZZ 連結函數作為候選，因為……，之後會用診斷確認」，讓使用者知道推理過程與這只是起點。

## Stage 3：模型配適

進入這階段時，先讀 `references/model-building-and-validation.md` 的 B、C 節，依下列順序進行：

1. **先檢查每一個連續解釋變數的函數形式**（不是只檢查其中一兩個，例如 income 這類變數也要檢查）。分組趨勢圖（二元 Y 用經驗 logit，計數 Y 用 log 平均數）只能提供線索，**不能只憑分組圖就決定轉換方式**；要再配合偏殘差圖，以及線性、`log()`、多項式、樣條的 AIC／BIC／概似比檢定比較。
2. **列出候選模型並編號**（m1、m2、…），並在看結果之前，先和使用者講好**選模原則**（例如巢狀用概似比檢定、非巢狀用 AIC／BIC、差距很小時選較簡單的、函數形式要合理）。
3. 用 `glm(y ~ x1 + x2 + ..., family = 分佈家族(link = "連結函數"), data = dat)` 配適各候選模型。**每配適一個模型，立刻做估計是否成功的檢查**（收斂、完全分離、係數與標準誤是否極端、擬合機率是否貼近 0 或 1、實際使用的觀測數，見 `references/model-building-and-validation.md` 的 F 節）；能輸出 `summary()` 不代表估計可靠。
4. **有系統地比較候選模型**：LRT 只用於可比較的巢狀模型，AIC／BIC 在使用相同分析樣本、可比較的概似模型時用來權衡配適與複雜度，**兩者與殘差診斷、研究合理性分開看，不混成同一套排名**。所有候選模型必須使用相同的分析樣本（用 `nobs()` 確認）；quasi-family 不能用一般的 AIC 或標準概似比檢定。並排呈現觀測數、參數個數、收斂狀況、AIC、BIC、殘差偏差。**不要因為某個模型的係數比較容易解釋，就忽略明顯的配適不足**；若較簡單的模型配適明顯較差，要如實告知使用者並由使用者決定。
5. 選定**最終模型**，明確講出是哪一個以及理由。之後的解釋、診斷、結論都以最終模型為準。
6. 對最終模型印出 `summary(model)`，並且：
   - **逐一解釋每個係數**：注意 GLM 的係數是在 link scale 上，一般人看不懂，要轉換成好理解的量：
     - `logit` link → 用 `exp(coef)` 講成 odds ratio（勝算比）
     - `log` link（poisson / Gamma）→ 用 `exp(coef)` 講成 rate ratio 或倍數效果
     - `identity` link（gaussian）→ 係數本身就是原始尺度的效果，直接解釋
   - 可用 `broom::tidy(model, conf.int = TRUE, exponentiate = TRUE/FALSE)` 整理成表格，用 `knitr::kable()` 呈現（不要用 `kable_styling()`）。
   - 依研究目的措辭：解釋關聯時說「關聯」，不要在沒有因果假設的情況下用因果語氣。
   - **解釋時必須交代**（細節見 `references/model-building-and-validation.md` 的 H 節）：類別變數的參照組、連續變數係數對應的增加單位、轉換後變數要依轉換後的尺度解釋（例如 `log1p(x)` 不能講成 x 增加 1 單位）、估計值盡量搭配信賴區間與 p 值、odds ratio 不是風險比也不能說成機率增加幾倍、樣條等非線性形式不能用單一係數概括，改用預測值或曲線呈現。
   - 報告模型實際使用的樣本數，以及因缺失值被排除的筆數。
7. 講清楚整體模型的解釋力／適合度的初步指標（例如 `performance::r2(model)` 給出的 pseudo-R²），但強調這只是初步，真正判斷模型好壞要看 Stage 4 的診斷與預測評估。

## Stage 4：模型診斷與評估

這階段是回頭檢查 Stage 2 選的 family/link 和 Stage 3 配的模型「站不站得住腳」。詳細的各家族診斷檢查清單、常見問題與對應補救方式放在 `references/diagnostics-checklist.md`，**進入這階段時務必先讀取那份參考檔案**，依裡面的項目逐一檢查，包含但不限於：

- 殘差診斷（deviance / Pearson residuals 對 fitted values 作圖），找系統性結構。**GLM 不要求殘差服從常態，Q-Q 圖不能用來判定「誤差是否常態」**
- 過度離散檢查：依資料形式解讀，不把某個離散比值當成統一門檻；**單筆 0/1 的 binomial 沒有可獨立估計的額外離散參數**，不要據此換模型；quasi-family 不會修正錯誤的平均數結構、遺漏變數或相依性
- 共線性（`car::vif()`）：VIF 是警示不是自動刪除變數的規則；含因子或多自由度項時要看 GVIF 的調整值
- 計數資料的零值：比較實際與預期的 0 個數，評估差異的大小與不確定性，**不用固定百分比當門檻**。若確實偏多，說明零膨脹與門檻模型的區別後即停止，**本 skill 不支援這兩種模型的配適**，請使用者另行處理
- 具影響力的觀測值（Cook's distance、leverage）：4/n 是警示線；列出高值觀測，檢查資料，有效資料不因統計量刪除，必要時做敏感度分析
- 適合度檢定：確認該檢定的資料結構與近似條件成立，條件不足時只當有限的診斷證據；單筆二元資料不把 Pearson 或 deviance 卡方當標準檢定，改看校準與預測評估
- 用 base R 的 `plot(model)`（`par(mfrow=c(2,2))` 四合一）當總覽圖，存成圖檔展示給使用者。這張圖不能取代依 family 選擇的診斷，四張圖也不適用同一套判讀標準（不要預設用 `performance::check_model()` 的畫圖功能，因為它依賴的 `see` 套件在此環境不一定裝得到）

**診斷之後，還要單獨做預測評估，兩者不能互相取代**：模型診斷檢查假設、影響點與配適問題；預測評估則用**樣本外驗證**（k 折交叉驗證或訓練／測試切分，所有候選模型用相同的折，二元資料用分層切分，指標彙整方式要明確定義，前處理只能用訓練資料估計以避免資料洩漏，指標依 family 選擇，見 `references/model-building-and-validation.md` 的 D 節）。研究目的是預測時，這是必做項目；其他目的時也要明講「診斷通過不等於預測能力良好」。

每一項檢查都要明講「這個檢查在看什麼、結果怎樣、可能的原因與處理選項」，並依「統計判斷與自動化決策原則」把診斷當作證據，不是自動決策規則。如果診斷發現問題嚴重到動搖 Stage 2/3 的結論，要明確告知使用者，並視情況回頭調整模型、重新配適並重新診斷，而不是隱瞞問題硬給一個「看起來很正式」的結論。

### Stage 4-1：結論要和最終模型一致

寫總結之前，先讀 `references/model-building-and-validation.md` 的 E 節：

- 明確寫出最終模型是哪一個，結論中所有估計值、診斷結果、預測指標，**都必須來自最終模型**。
- 若選了較複雜的模型（例如 m4），就以 m4 的估計為主要結論；若保留較簡單的模型（例如 m2），要清楚說明簡化的目的與配適限制（例如概似比檢定顯示 m4 顯著較佳）。
- **不要混用不同模型的結果而不交代**；引用其他模型的數字時，要標明是哪個模型、為什麼引用。
- 寫完後回頭檢查：結論中的每個數字是否都能對應到最終模型的輸出。

## 輸出形式：對話中呈現 vs 產出報告檔案

兩種都要能做，依使用者當下的要求決定（沒特別說的話，預設直接在對話中逐步呈現文字、表格、圖）：

- **對話中呈現**：每個階段的 R 程式碼只在背景執行（用環境可用的 R 執行工具），**回覆中不要貼 R 程式碼**，除非使用者明確要求看程式碼。回覆只呈現執行結果（整理成易讀的表格與數字）、圖檔（用環境提供的方式展示）以及對結果的白話解釋，依 Stage 1-4 的順序分節說明。使用者沒有要求就不要主動提供程式碼，也不要說「程式碼如下」。
- **產出報告檔案**（使用者要 PDF / HTML / Word 報告時）：用 `assets/report_template.qmd` 當骨架複製一份出來修改（這是使用者習慣的 Quarto 範本，一份檔案同時支援 pdf、html、docx 三種輸出），內容依 Stage 1-4 填入對應的程式碼與文字說明，再用 `LC_ALL=C.UTF-8 quarto render report.qmd --to pdf`（或 `html`、`docx`）轉出。圖表要用 `#| label: fig-xxx` / `tbl-xxx` 搭配 `#| fig-cap:` / `#| tbl-cap:` 寫標題，內文用 `@fig-xxx` 交叉引用，章節標題用 `#`（編號由 `number-sections` 自動產生）。使用者只要其中一種格式時，把 YAML 裡其他 format 區塊刪掉。轉出的檔案放到目前環境實際支援的輸出位置，並用環境提供的檔案傳送方式交給使用者。若使用者只說「報告」沒指定格式，先問一句要哪種檔案格式。範本內的字型設定、YAML 結構不要隨意更動，這是使用者自己的版面偏好。

完整分析模式下，不論哪種輸出形式，都必須完整走過 Stage 1-4，不能因為要產出報告檔案就把逐步解釋省略掉、只留下結果表格。報告中的所有數字都要對應到最終模型。
